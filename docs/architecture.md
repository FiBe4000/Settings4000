# Settings4000 — Technical Architecture

Companion to `docs/requirements.md` (R-numbers referenced throughout) and `docs/dotfiles_analysis.md`.

## 1. Technology stack

| Concern | Choice | Notes |
|---|---|---|
| Language | **Rust** (stable, 2024 edition) | Single binary, fast cold start (R8.1) |
| GUI | **GTK4 via `gtk4-rs`, structured with Relm4** | Relm4 components give declarative message-driven UI; the core state machine lives outside widgets (R6.2) |
| Testing | **`cargo test`** (built-in harness) + `tempfile` for fixture dirs, `assert_matches`/snapshot comparison for round-trip tests | No extra runner; CI/pre-commit gate is plain `cargo test` (R6.1) |
| Logging | **`tracing`** + **`tracing-journald`** layer, `tracing-subscriber` fmt layer to stderr as fallback | journald per R7.1; `EnvFilter` honors `SETTINGS4000_LOG`/`RUST_LOG` and `--log-level` (R7.2) |
| Single instance | `gtk::Application` with a fixed application ID | GApplication D-Bus activation raises the existing window (R8.4) |

## 2. Crate / module layout

```
settings4000/
├── src/
│   ├── main.rs            # CLI args, logging init, gtk::Application bootstrap
│   ├── ui/                # Relm4 components: window, sidebar, category pages
│   ├── core/              # GTK-free, fully unit-testable (R6.2)
│   │   ├── store.rs       # SettingsStore: staged edits, dirty tracking, conflict detection
│   │   ├── detect.rs      # installed-app detection
│   │   ├── apply.rs       # transactional writes + reload orchestration
│   │   └── model.rs       # typed Setting values + validation (R8.3)
│   ├── parsers/           # one module per file format (see §3)
│   └── system/            # side-effect boundary: CommandRunner trait, file IO, journald
└── tests/                 # integration tests against fixture dotfiles
```

Hard rule: `core/` and `parsers/` never import `gtk`. All process execution goes through a `CommandRunner` trait so integration tests inject a mock recorder (R6.1).

## 3. Dotfile parsing & safe modification

Principle: **surgical, span-preserving edits** — never serialize a whole file from a model (R5.3.1). Each parser produces a lossless line/token representation; the writer replaces only the value span of a targeted key and re-emits everything else byte-identical. Every parser has round-trip tests (`parse → edit nothing → emit == input`).

Per-format parsers (`parsers/`):

| Format | Files | Strategy |
|---|---|---|
| Palette kv | `colors/<scheme>` | Line-oriented `key=hex`; edit value in place. Validated against the generator's key list (18 keys today, `shadow` included — read from `scripts/generate-colors`'s `NAMES=(…)` line, built-in list as fallback) before write |
| hyprlang | `hypridle.conf`, `hyprlock.conf`, `hyprpaper.conf` | Tokenize into lines: comments, `key = value`, `section {` / `}`, `source=`. Edits address a key by *section path* (e.g. `input.touchpad.natural_scroll`) and rewrite only that line's value. **Repeatable top-level keys** (`env=`, `exec-once=`) are addressed by key + first comma-field (e.g. `env:XCURSOR_THEME` matches the `env = XCURSOR_THEME,…` line) and only the value portion after that field is edited. Commented-out lines are never matched. A key duplicated within a section is edited at its **last** occurrence — hyprland applies config top-to-bottom (last assignment wins), so editing an earlier shadowed copy would have no effect; same rule as the env/INI editors (task 9.8). New keys are appended at the end of their section. Hyprland itself runs the **Lua** config provider (analysis §7.1, §8.6): the former `input.conf`/`hyprland.conf` no longer exist, so the input/cursor edits route to the Lua-literal editor below and this parser serves only the three hypr* daemon files. Token-level edits inside a value (the `--grace N` of hypridle's `lock_cmd`) are done on the value string returned by this parser |
| Lua literal | `config/hypr/input.lua` (one flat `hl.config({ input = { … } })` table, app-owned), `config/hypr/hyprland.lua` (**only** the two `hl.env("XCURSOR_THEME", "…")` / `hl.env("XCURSOR_SIZE", "…")` lines) | Line-oriented, not a Lua parser: track `{`/`}` nesting of table constructors to compute the *table path* of each `key = <literal>,` line (`input.touchpad.natural_scroll`), and rewrite only the literal — a double-quoted string (escapes preserved, `"` and `\` in new values rejected), a bare number, or `true`/`false`. `--` comments and blank lines are byte-preserved. Keys absent from the table (`kb_variant`, `kb_model`, `kb_rules`) are **inserted** as a new `key = "value",` line at the end of their table, matching the file's indentation. Hyprlang `tap-to-click` is `tap_to_click` here. For `hyprland.lua` the editor addresses the two `hl.env` call lines by their first string argument and only rewrites the second; everything else in that file is code the app never touches. Same last-occurrence rule as hyprlang. Round-trip and nesting-fidelity tests are taken from the live files (analysis §7.1) |
| monitors.conf | `config/hypr/monitors.conf` | Parse `monitor=` records (name/desc, mode, position, scale, trailing key/value pairs) preserving surrounding lines. Later-rule-wins semantics respected: edits modify the matching record for the target monitor, or append after the last `monitor=` line. Hyprland no longer reads the file itself: `hyprland.lua` parses it into `hl.monitor()` calls and `hypr-display-profile.sh` awk-parses the eDP rule, so the grammar is **frozen** (analysis §7.2) and the writer validates every emitted record against it: fields in the fixed order `output,mode,position,scale[,key,value…]`, no `,` or `#` inside values (`desc:` strings included), the output token immediately followed by `,`, one rule per eDP key, the catch-all first, and a `disabled` extra only as `disabled,1` and never on an eDP key. An external output is turned off and on by adding and removing exactly that pair (task 10.4), so its other extras (`bitdepth,10`) survive. The app never touches either script |
| INI | `gtk-3.0/settings.ini`, `gtk-4.0/settings.ini`, `~/.icons/default/index.theme` (`[Icon Theme]` → `Inherits=`, the XCursor fallback — analysis §8.4) | Minimal line-preserving kv-in-section editor. All three files are tracked in the dotfiles and symlinked by `setup.sh` (analysis §6.5, §8.4), so editing an existing section is the norm; the create-file-if-absent path remains a fallback for non-dotfiles users. A live file may have been **de-symlinked by an external tool** (`nwg-look` once did this to `gtk-4.0/settings.ini`, analysis §7.7; re-linked since): the writer edits whatever the XDG path resolves to and the startup loader reports a plain live file whose repo twin exists as a divergence note, never silently writing the repo copy GTK does not read. `gtk-xft-dpi` is never written (the dotfiles removed it deliberately) |
| notifd config kv | `~/.config/notifd/config` (seven `key=value` lines, analysis §8.2) | Reuses the palette kv parser's line model (bare `key=value`, `#` comment lines, blank lines preserved; `key = value` whitespace tolerated on read, written back in the file's own spacing; inline comments after a value are invalid to the daemon and therefore never emitted). Validation mirrors the daemon's: integers `0..2^31-1`, `history_max ≥ 1`, `critical_per_app` in `1..5`, booleans written as `true`/`false`. Reload is the daemon's `Reload()` method, never a unit restart |
| notifd runtime (no parser) | D-Bus `se.dotfiles.Notifd` | `GetState()` (signature `bubb`: dnd, count, inhibited, center_open — a pure query) is parsed from `busctl`'s typed output; actions are `SetDnd s on|off`, `Clear`, `SetCenter s open`, `Reload`, all as `busctl --user --auto-start=no call se.dotfiles.Notifd /se/dotfiles/Notifd se.dotfiles.Notifd <method> …` through `CommandRunner` — the same calls `scripts/notifctl` makes. `GetServerInformation` version `≥ 1.1` gates `GetState`/`Reload` and the file-backed rows; the item/history JSON files hold message bodies and are never read. The former `swaync/config.json` JSON editor is retired with swaync |
| env file | `config/uwsm/env` | Targeted `export KEY=value` line edits for `XCURSOR_THEME`/`XCURSOR_SIZE`; commented lines detected but not modified (used for the `GTK_THEME` warning, R3.3) |

Generated files are **read-only inputs** — never written directly. `generate-colors` produces **six color partials** (`config/hypr/colors.conf`, `config/hypr/colors.lua`, `eww/_colors.scss`, `rofi/colors.rasi`, `kitty/colors.conf`, `zsh/colors.zsh` — the former `swaync/colors.css` is no longer generated, analysis §8.3), **three font partials** (`kitty/fonts.conf`, `eww/_fonts.scss`, `rofi/fonts.rasi` — templated from `theme/fonts`, analysis §6.5), and the `state/active-scheme` marker. Headers all read `# Generated from colors/<scheme> — do not edit manually` behind the format's comment prefix (`#`, `//`, `/*`, and `-- ` for the Lua file). The app reads only `colors.conf`'s header to detect the active scheme (R3.2), and optionally the marker; fonts are out of v1 scope (requirements §9). The palette schema is **18 keys** (`shadow` joined the original 17, analysis §7.6); the parser takes the key list from the script's `NAMES=(…)` line when the script is readable and falls back to the built-in 18-key list, so a future key does not make valid schemes fail validation. All palette changes go through editing `colors/<scheme>` + running `scripts/generate-colors`.

### Write safety (R5.4, R5.6)

- On first read, the store records each file's content hash + mtime. Before Apply (and on window focus/manual refresh) files are re-read; a mismatch triggers a conflict warning and reload of staged views instead of a silent clobber. Only a mismatch in a file the Apply would *write* aborts it: a tracked file the Apply does not touch cannot be clobbered by it, so that mismatch is reported to the user (Refresh reloads it) rather than blocking every category's Apply until the file is fixed — which it would do indefinitely for a file the store cannot re-baseline, i.e. one that was deleted, made unreadable, or left unparseable (task 9.11).
- The app **addresses every backing file by its XDG runtime path** (`$XDG_CONFIG_HOME`/`~/.config`, and the equivalent per-app paths), never a hardcoded `~/.dotfiles` path (R8.5) — so it behaves identically for this symlink-deployed setup and for a user with plain config files. Apply writes each file as: write full new content to `NamedTempFile` in the same directory as the *resolved* target → fsync → atomic `rename` over that target. The writer `fs::canonicalize`s first: when the XDG path is a symlink into a dotfiles repo it rewrites the repo file and leaves the link intact; when it is a plain file it rewrites it in place. Either way the temp file lives beside the real target so the rename is atomic and cross-device-safe.
- Apply is per-file transactional: files are written in sequence; on any failure, already-written files are restored from their pre-apply snapshots (kept in memory), the error is surfaced, and staged state is retained for retry.
- Validation (R8.3) runs on the typed model before any write: hex format, monitor mode strings (`WxH@Hz`), numeric ranges for timeouts/sensitivity/scale, file paths (exists + readable + image extension for wallpaper/lock background), and — for every theme name and image path — the strictest character rule any of its target writers applies (`core/value_writers.rs` asks the INI, env, hyprlang and Lua writers, the GTK 4 link step and the hyprpaper request for their own rules, so a value is refused at stage time instead of being written to some copies and refused by others; task 9.27). Step 1 of the Apply pipeline re-checks every write against the `SettingId`s it declares in `validated_by`.

## 4. Installed-app detection & dynamic visibility (R4)

`core/detect.rs` runs once at startup (async, before window population; re-runnable via a refresh action, R4.3):

- **Binary presence**: manual `$PATH` scan (executable file check per dir) rather than shelling out to `which` — testable with an injected `PATH` string (R6.1 detection tests).
- **Daemon liveness** where relevant: Hyprland via existence of `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket.sock` (plus `hyprctl` on `$PATH` — nearly every reload needs it); hypridle/hyprpaper/eww/kitty via `pidof`-equivalent (procfs scan), plus `xsettingsd` as an informational-only signal that an external GTK-settings writer is active (task 11.12, §5); NetworkManager via `nmcli` presence; settings-portal availability (`xdg-desktop-portal-gtk` process or dconf backend) for the R2.2 live-restyle claim.
- **Hyprland config provider** (analysis §7.1): `hyprctl status` → `configProvider: lua` or `hyprlang` when a session runs, else whether `~/.config/hypr/hyprland.lua` exists. It is a guard, not a router: the app's Hyprland-side input and cursor writes exist only for the Lua files (`input.lua`, the two `hl.env` lines), so a hyprlang session hides the Input page and the Hyprland-side cursor write and logs it at `info` (analysis §8.6); live tweaks always use `hyprctl eval`.
- **Notification daemon** (analysis §7.5, §8.2): notifd is detected by `busctl --user call org.freedesktop.DBus /org/freedesktop/DBus org.freedesktop.DBus NameHasOwner s se.dotfiles.Notifd` (true only while notifd runs), cross-checked with `systemctl --user is-active notifd.service`; a linked `~/.config/systemd/user/notifd.service` with no owner means "installed, will D-Bus-activate", which still enables the runtime rows. A running daemon is then asked `GetServerInformation` (`--auto-start=no`): version `≥ 1.1` enables the file-backed rows, `GetState` and `Reload`; older daemons get the runtime-only page. The probe never auto-starts anything and never calls `swaync-client` (a `swaync` binary may still be installed — binary-on-PATH is a false positive for it).
- **Dotfiles palette source** (R3.2, R8.5): canonicalize a deployed config symlink (e.g. `~/.config/hypr/colors.conf`) to find the repo root, then check for `colors/` + `scripts/generate-colors`. A non-symlinked config (i.e. no dotfiles repo behind it) or a missing source gates the palette switcher off — it is hidden like a missing app rather than pointing at a guessed path.
- **Config readability** (R4.4): each backing file is checked readable+parseable at its XDG path; failures hide the affected controls and log `warn`.

The result is a `Capabilities` struct (plain data). Each settings row/page declares its required capability; the UI builder skips rows whose capability is absent and hides a category entirely when all its rows are gone (R4.2), logging each hidden item at `info`. No detection failure aborts startup — detection errors degrade to "absent".

## 5. System color / theme ingestion (R2)

The app performs **no palette ingestion for its own styling**: as a GTK4 app it inherits the active system GTK theme automatically (R2.1). No custom CSS is shipped. **Live** re-styling on theme change (R2.2) is *not* native on Hyprland: GTK4 reads `settings.ini` only at startup and picks up runtime `org.gnome.desktop.interface` changes only via the settings portal (`xdg-desktop-portal` + `xdg-desktop-portal-gtk`) or the dconf GSettings backend. Detection checks for that path; when absent, theme changes take effect at next launch and the UI says so (see §10).

Colors are read only as *data* for the Theme page:

- Active palette scheme: header line of the deployed `~/.config/hypr/colors.conf` (R3.2). Available schemes: directory listing of the dotfiles `colors/` dir, located by canonicalizing a deployed config symlink (`~/.config/hypr/colors.conf` → `<repo>/config/hypr/colors.conf` → repo root) rather than assuming `~/.dotfiles`; if that resolution fails (no dotfiles repo behind the config), the palette switcher is an absent capability and hidden (R4, R8.5).
- Current GTK/icon/cursor theme: `gsettings get org.gnome.desktop.interface {gtk-theme,icon-theme,cursor-theme,cursor-size}`, cross-checked against `settings.ini`; installed themes discovered per R3.3/R3.4 directory scans. (Decision: v1 shells out to `gsettings` through `CommandRunner` for uniform logging/mocking; switching to in-process `gio::Settings` — dropping the binary dependency and its detection entry — is a noted later simplification.)
- A `GTK_THEME` env var, if set in the app's own environment or found uncommented in `config/uwsm/env`, triggers a persistent info banner and disables the GTK-theme drop-down (R3.3 — never fight the override). (The former `scripts/launchhyprland.sh`, which exported it, is deleted; the session is now started by the display manager through `uwsm`, and on the target host the variable is unset everywhere — analysis §7.7.)
- Two external tools rewrite the same GTK settings on the target host — kded6's gtkconfig module (suppressed at Hyprland start by `scripts/kded-gtkconfig off`) and `nwg-look` (installed but, by decision, not to be run — analysis §7.7, §8.4). The R5.6 freshness check already catches their edits; the Theme page additionally notes when `xsettingsd` is running or a `settings.ini` is a plain file beside a repo twin, since both mean a later rewrite is likely.
- GTK 4 / libadwaita apps on this desktop take their theme from three symlinks `~/.config/gtk-4.0/{gtk.css,gtk-dark.css,assets}` → `/usr/share/themes/<gtk-theme-name>/gtk-4.0/…` that `setup.sh` creates from `settings.ini` (analysis §8.4). A GTK-theme change therefore has a third leg beside gsettings and the INI files: re-point the three links when the chosen theme has a `gtk-4.0/gtk.css` under one of the R3.3 theme roots, remove them (with a note) when it does not, and leave a plain file at any of those paths untouched with a warning (task 11.16). The theme roots are searched in GTK's own lookup order — `$XDG_DATA_HOME/themes`, `~/.themes`, each `$XDG_DATA_DIRS` entry's `themes/` (default `/usr/local/share:/usr/share`), then GTK's built-in `<prefix>/share/themes` (`_gtk_css_find_theme` in GTK 4's `gtkcssprovider.c`) — and the first root carrying the theme's `gtk-4.0/gtk.css` is linked, so for a theme installed twice the links point at the copy GTK 4 itself would load (task 10.6). When `~/.config/gtk-4.0` is itself a symlink to a directory (e.g. into the dotfiles repo), the links are placed inside the directory it points to and the directory link is kept, like every other write through a deployed symlink.

Optional nicety: the palette drop-down renders small swatches per scheme by parsing each `colors/<scheme>` file — display only, no styling impact.

## 6. Apply pipeline & reload mechanism (R5)

Staging: the `SettingsStore` holds `original` and `staged` typed values per setting; dirty = any difference. Runtime-only controls bypass the store (R5.2) and execute immediately: volume/mute via `wpctl set-volume`/`wpctl set-mute`, default output/input device via `wpctl set-default <id>` (devices enumerated from `pw-dump` JSON, falling back to parsing `wpctl status`), and the laptop-display toggle, which runs the dotfiles' `scripts/hypr-toggle-laptop-display` (located via the repo root, R8.5) after reading the current eDP state from `hyprctl monitors all -j` (`all` so a disabled panel is still listed, with `"disabled": true`; the state is read again afterwards and the switch shows that read, since the script is a pure toggle) — the script issues the `hl.monitor` call, maintains `/tmp/hypr-laptop-display-forced`, and relaunches the eww bars (analysis §7.3); the app never writes a `monitor=…,disable` record, which the hotplug watcher would fight, and never re-implements the script's steps. Because the script can outlast the 5 s runner timeout (its bar relaunch may restart the eww daemon, and the runner then still waits for the orphaned launcher to close its inherited pipes), the read–script–read sequence runs on a worker thread through the same main-thread hop as the startup load, and the switch stays insensitive until the re-read returns (task 10.3) — or, should it never return (a wedged grandchild keeps the inherited pipes open), until a 30 s watchdog re-enables it at the last read state with a note; nothing is killed, and a late outcome is ignored so it can never finish a newer toggle (task 10.7). Notifications are runtime-only too: DND/clear/open-center go straight to notifd's D-Bus interface (§3). Reset drops `staged`.

On **Apply**, `core/apply.rs` executes a fixed-order plan:

1. **Validate** all staged values (abort before any side effect on failure).
2. **Conflict check** (re-read + hash compare, §3) — a changed file among the plan's write targets aborts the Apply; a changed tracked file it does not write is reported to the user, not blocking (§3 "Write safety").
3. **Write files** atomically (§3). If the palette scheme changed: edit nothing generated — run the discovered repo's `scripts/generate-colors <scheme>` (located per §5/R8.5) as a child process and treat non-zero exit as a write failure (the script validates and fails loudly without partial output). The generate-colors step runs **last** among the write steps: per-file rollback only restores app-written snapshots, so ordering it last guarantees a failure elsewhere never leaves the generated files (the six color partials, three font partials, and the marker — §3) on the new scheme while everything else is rolled back. Note `generate-colors` now also depends on `theme/fonts` (analysis §6.5) and aborts if it is missing/incomplete, so a broken font source surfaces here as a palette write failure — already covered by the non-zero-exit handling.
4. **Reload** affected components — only those whose backing file actually changed *and* which detection found running (this set mirrors `scripts/apply-theme`, the canonical CLI wrapper — analysis §6.1 — and must be kept in sync):

| Component | Mechanism |
|---|---|
| Hyprland | `hyprctl reload config-only` for input, cursor and palette changes (mirrors `scripts/apply-theme`; it skips the compositor's own monitor re-apply) and the full `hyprctl reload` when `monitors.conf` changed. Both forms are docked-safe since the dotfiles' Lua monitor loader derives the docked state from `hl.get_monitors()` and keeps the laptop panel disabled across reloads (analysis §8.1); `config-only` alone was never a safety mechanism, so the app needs no docked warning. hyprctl speaks the IPC socket for us. Simple live tweaks use `hyprctl eval '<lua>'` — `hyprctl keyword` answers `keyword can't work with non-legacy parsers` on the Lua provider; `ok` on stdout is success |
| eww | `eww reload`. Non-fatal on failure with the message surfaced: it aborts before reloading CSS when a stale `bar-<monitor>` id cannot reopen, and it resets every `defvar` (analysis §7.8). The app never restarts the eww daemon (tray icons are lost) and never opens bars itself |
| notifd | No reload for a palette change (its popups are eww widgets styled from `_colors.scss`, covered by `eww reload`). The D-Bus method `Reload()` on `se.dotfiles.Notifd` (equivalently `systemctl --user reload notifd.service`, which sends SIGUSR1) when `~/.config/notifd/config` was written **or** the icon theme changed — notifd re-reads both without dropping popups, timers, inhibitors or history (analysis §8.2). The daemon reads the icon theme only from `gtk-3.0/settings.ini`, which the INI writer covers. Never a unit restart, never SIGHUP (that stops it), never `swaync-client` — analysis §7.5 |
| kitty | `SIGUSR1` to all kitty PIDs (sent directly via `nix::kill`, no shell). Remote control is now enabled in the dotfiles (`allow_remote_control socket-only` + per-instance socket, analysis §6.1), so a later switch to flicker-free `kitten @ set-colors` is unblocked; v1 keeps SIGUSR1 |
| hyprpaper | `hyprctl hyprpaper wallpaper ,<absolute path>[,contain\|tile]` — one request; `preload` is not a hyprctl request on hyprpaper 0.8 (task 11.10), and the fit field is sent only for the two modes the IPC renders differently from cover (task 11.14); then `<config>/eww/scripts/bar-text-tone --apply` after `eww reload` when the script exists and eww is live |
| hypridle | restart: `systemctl --user try-restart hypridle` if unit exists, else kill + respawn detached |
| hyprlock | **none (intentional)** — hyprlock reads its config at launch, so changes take effect at the next lock |
| GTK theme/icons/cursor | `gsettings set ...` + `hyprctl setcursor <theme> <size>` (works on both config providers); the cursor value is written identically to every place the app owns — both `settings.ini` and `~/.icons/default/index.theme` (`Inherits=`, via the INI writer), the two `hl.env` lines in `hyprland.lua` (Lua-literal editor), and `uwsm/env` in step 3 — so the unified duplicates (currently `breeze_cursors`/24) stay equal (R3.4, analysis §7.7, §8.4). Env-file copies take effect at the next login, which the page says |
| GTK 4 theme links | after a `gtk-theme-name` write, re-point `~/.config/gtk-4.0/{gtk.css,gtk-dark.css,assets}` at `<theme root>/<name>/gtk-4.0/…` (filesystem step, not a command — done in the write phase with its own rollback snapshot of the old link targets); removed with a note when the theme has no `gtk-4.0/gtk.css` under any root; a plain file at any of the paths is left alone and reported (analysis §8.4, task 11.16) |
| hyprpaper + bar | after a wallpaper change, additionally `~/.config/eww/scripts/bar-text-tone --apply` when present, so the bar re-picks its text colour from the new image (analysis §7.8; best-effort, non-fatal) |

All reloads go through the `CommandRunner` trait: spawned without a shell (`Command` with arg vectors — no injection surface), 5 s timeout, exit status + stderr captured. A failed reload is logged at `error` and shown as a non-fatal toast; file writes stand (R5.5). Every write and reload is logged per R7.3.

## 7. UI architecture

- Plain `GtkApplicationWindow` with sidebar `GtkStackSidebar` (categories from §3 of requirements) + content `GtkStack`; scales for the 1.33-scaled laptop panel and 1440p monitors (R2.4). **libadwaita is deliberately not used**: it hard-codes the Adwaita stylesheet and ignores `gtk-theme-name`, which would violate R2.1/R2.2.
- Each category page is a Relm4 component that renders rows from a declarative row list (`label`, `widget kind`, `setting id`, `required capability`). Widget kinds per R2.3: `GtkDropDown` (choices), `GtkSwitch` (booleans), `GtkScale` (continuous).
- Widgets are thin: they emit `SetValue(setting_id, value)` messages to the store and re-render from store state. Dirty state drives a suggested-action **Apply** button + per-page dot markers, with **Reset** alongside (R5.1). All staging/dirty/conflict logic is in `core/` and headlessly tested (R6.2).
- Sound page reads PipeWire state on page entry from `pw-dump` JSON (fallback: parsing `wpctl status`); device switching via `wpctl set-default <id>` (v1; event subscription via `pw-mon` deferred). Network page is read-only status (`nmcli -t`) + an "Open Network Settings" button that spawns `kitty -e nmtui` (gated on the kitty capability) or `nm-connection-editor` when installed (R3.1) — re-launching the autostarted `nm-applet` or a terminal-less `nmtui` is not viable.
- The header bar additionally carries an app menu (`gtk::MenuButton` + `gio::Menu`) with an **About** entry (R2.5, task 10.2). The About window's name/version/author/repository-link fields come from the Cargo package metadata at compile time (`env!("CARGO_PKG_*")` — one source shared with `--version` and the startup log, R8.6). `gtk::AboutDialog` is deprecated from GTK 4.10, so if it does not compile clean under `-D warnings` with the enabled gtk4 features, a plain modal window (the same precedent as the §5.3-era conflict dialog, with `gtk::LinkButton` for the link) is used instead.
- **Packaging (R8.7, §12 of `docs/tasks.md`).** Desktop integration is three artifacts named after the GApplication ID (R8.4) — the binary `settings4000`, the desktop entry `data/org.settings4000.Settings4000.desktop` and the icon `data/org.settings4000.Settings4000.svg` — and the package adds the `LICENSE` text (MIT). Two installers place them under two prefixes: `install.sh` under `~/.local` (no root; the desktop entry's `Exec=` is rewritten to the absolute `~/.local/bin` path) and the Arch package `packaging/arch/settings4000-git/PKGBUILD` under `/usr` (entry installed verbatim, license under `/usr/share/licenses/settings4000-git/`). The two must not be mixed, since a per-user desktop entry shadows the system one. The version has one source, `Cargo.toml` (R8.6): the PKGBUILD's `pkgver()` reads it from the checked-out tree, and its `pkgver=0` is only makepkg's required placeholder. Guard tests in `src/ui/app.rs` pin the app id in all artifacts and both installers, and the PKGBUILD's `url`, `license`, version source and `optdepends` (the package of every detected tool not already a dependency, R4); the `arch-package` CI job builds the package in an `archlinux:latest` container, checks `.SRCINFO`, runs the test suite in `check()` and fails on any `namcap` warning outside its allow-list.

## 8. Startup sequence (budget: <500 ms, R8.1)

1. Parse CLI, init tracing (journald or stderr fallback).
2. `gtk::Application::register` — if another instance holds the ID, activate it and exit.
3. Run detection + parse all backing files concurrently on a worker thread while GTK builds the window shell.
4. Populate pages when detection/parsing completes; log detection summary at `info`.

## 9. Testing strategy (R6)

- **Unit** (`src/**` `#[cfg(test)]`): every parser — round-trip identity, targeted-edit exactness (comments/order/commented-out lines untouched), malformed-input tolerance; store staging/dirty/reset/conflict transitions; validators.
- **Integration** (`tests/`): fixture copy of the real dotfiles tree in a `tempfile` dir; scenarios stage edits → Apply → assert exact resulting file bytes; `CommandRunner` mock asserts the exact reload commands (and their order) for each change class, including failure injection for R5.4/R5.5 paths.
- **Detection**: fake `PATH` dirs with dummy executables; assert `Capabilities` and hidden-row outcomes.
- CI/pre-commit: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`.

## 10. Key risks / decisions

- **hyprlang writer fidelity** was the highest-risk parser (nested sections, `source=`, comment preservation); mitigated by exhaustive round-trip fixtures taken from the live dotfiles. Its exposure shrank with the Lua switch: on the target host it now serves only `hypridle`/`hyprlock`/`hyprpaper`. The new risk is the **Lua-literal editor**: `input.lua` is deliberately "schema-flat, one `hl.config` call, no logic" (its own header), which keeps a line-oriented editor sound, but `hyprland.lua` is real code — the editor touches exactly two `hl.env` lines there and refuses anything else. If the dotfiles ever put logic into `input.lua`, the editor must detect it (unbalanced or non-literal lines) and hide the page rather than guess.
- **Lua only**: the frozen hyprlang `hyprland.conf`/`input.conf` were deleted (analysis §8.6), so there is no second flavour to keep in sync; the provider check remains as a guard for foreign hosts, where the Input page and the Hyprland-side cursor write are simply hidden.
- **Duplicated values**: cursor env (`hyprland.lua` + `uwsm/env` + both `settings.ini` + `~/.icons/default/index.theme`, all `breeze_cursors`/24) and wallpaper vs hyprlock background (same path, now written with `~`) are handled **write-both-identically**. The monitors-vs-profile-script duplication is **gone** — `hypr-display-profile.sh` derives eDP mode/scale from `monitors.conf` (analysis §6.2), so the app edits one record (kept parseable by both the awk and the Lua parser, §7.2) and issues no sync warning.
- **notifd's config surface is a daemon contract** (analysis §8.2): the seven keys, their ranges and the "invalid value falls back to the default" rule live in `scripts/notifd`; the app mirrors them in its validator and gates the file-backed rows on `GetServerInformation` ≥ 1.1, so a mismatch surfaces as hidden rows or a validation message rather than a daemon that silently ignores the file. Geometry (slots, anchor, width) stays out of scope — it is eww widget code.
- **Live theme propagation** (R2.2) depends on `xdg-desktop-portal-gtk` (or the dconf GSettings backend) being present — not guaranteed on Hyprland. Detection checks for it; acceptance is "restyles live when the portal/dconf path is active, on next launch otherwise", and the UI communicates which applies.
- No root, user files only (R8.2); no shell interpolation anywhere in command execution.
